# Stage capability audit and simplification proposal

Written 16 Aug 2026. Ground-truthed directly against the live Pi (`pi@192.168.1.106:/home/pi/stage/`) — `server.js`, `live-edit-routes.js`, `workstreams-routes.js`, `manifest.js`, `engagement-access.js`, `views/admin.html`, `views/client-home.html`, `views/admin-engagement.html`, and every `engagements/*/manifest.json` — not from memory. Supersedes the "three overlapping surfaces" framing in the brief with a more precise finding: there are two engines glued together, not three.

## 0. The one-sentence finding

Stage is not three tools competing for the same job. It is **two independent engines** (a legacy sign-off/review engine and a newer live-edit engine) **sharing one admin list**, plus **one dead engine** (a content-review mode that was never adopted). The confusion the brief describes is real, but its root cause is that the manifest schema lets an engagement carry two unrelated "type" signals at once (`modes[]` and `liveEditable`) with no single field saying what an engagement actually *is*.

## 2. The actual architecture (not the brief's three-surface framing)

Two genuinely separate engines exist in the codebase:

**Engine A — legacy review** (`shell.html`, `views/partials/{prototype,gallery,copy}.html`, `signoff.js`, `review-state.json`, `admin-state.json`, `admin-copy.json`). Client visits static prototype pages, approves/flags images and copy per section, hits a one-shot sign-off lock that generates `signoff.md`. Built for a single terminal handoff.

**Engine B — live-edit** (`live-edit-routes.js`, `public/live-edit.js` injected into deployed Astro HTML, `client-edits.json`, `client-comments.json`, `output/submissions/NNN.json`). Client edits the real page inline — copy, images, whole repeatable items, whole sections (clone/hide/reorder) — with no lock, and submits a versioned publish-request that Osman manually merges. Built for ongoing iteration.

These are not modes of one system. They have **different data models, different frontends, different completion semantics** (lock-once vs. submit-repeatedly). The only things they share are auth (`auth.js`), engagement access control (`engagement-access.js`), the manifest loader, and — recently, well — the admin engagement list grouped by client (`admin.html`, added 10 Aug).

**What conflates them:** every manifest, including live-edit ones, still carries a `modes: []` array (a legacy-review-only concept — it's what `workstreams-routes.js` calls "workstreams" and toggles on/off). But for a live-edit engagement, `modes` doesn't actually govern anything the client experiences; `liveEditable` alone decides which engine serves the page (`server.js:704-738`, `servePrototype()`). So an admin looking at the Workstreams tab for `puremed-micro` sees prototype/copy toggles that are vestigial — the real capability switch (`liveEditable`) isn't exposed there at all, it can only be set by hand-editing `manifest.json` on the Pi.

**The dead third engine:** `workstreams-routes.js` defines a `posts` mode ("Social content review") requiring an `items` field. No manifest in production has ever populated it. It's speculative generality that's been sitting in `KNOWN_MODES` since the Workstreams admin panel shipped, selectable in a UI with nothing behind it.

## 4. Concrete gaps, from a web designer's chair

Running client sites day to day on this tool, in priority order:

1. **No image reordering inside a multi-image module** (galleries, review strips, carousels). Only single-slot swap + reposition + resize exists. Real gap.
2. **No admin copy-editing on live-edit engagements.** A designer prepping a page before handoff can pre-fill or adjust starting copy on a review engagement (`admin-copy.json`) but not on a live-edit one — the only route in is editing the Astro source directly, or acting as the client through the live editor.
3. **No cross-page section move**, only within-page reorder (`section-order/:pageId`).
4. **No template/clone-engagement flow.** Each new treatment microsite is a hand-built engagement folder + manifest. With 7 treatments planned, that's 7 manually maintained folders with no shared lineage — the client-grouping in `admin.html` is a display-layer patch over this, not a data fix. This is the sharpest scaling problem in the system.
5. **No version history or rollback**, despite the data existing — every submission is already snapshotted in `output/submissions/NNN.json`, but nothing surfaces a diff or a "restore to submission #3" action.
6. **No responsive/mobile preview toggle** in the editor — all editing happens in whatever viewport the browser window happens to be.
7. **No structural guardrails.** Inline HTML is sanitized for *safety* (script/style/event-handler stripping) but not for *brand consistency* — nothing stops a client from reformatting text in a way that breaks a component's intended structure.

What's genuinely strong and worth keeping as the foundation: editing the real deployed HTML (kills prototype-vs-live drift for good), the webp pipeline, the aspect-ratio-mismatch guard, section hide/clone/reorder, and comment pins — this is a more capable editor than the brief gave it credit for. The gap is less "build more features" and more "finish wiring what's already half-built, then stop growing the legacy side."

## 5. UX: why it doesn't feel intuitive

- **The client-home ("Your reviews") already half-solves this** — it renders a different card ("Edit your site" vs. "Signed off"/"In progress") depending on `liveEditable`. But it still lists every engagement folder as its own card, including the dead review/content ones (hidden from *this* client only if an admin remembered to flip the visibility toggle — nothing prevents a stale engagement from surfacing).
- **Admin's per-engagement tabs don't adapt to what the engagement can do.** `admin-engagement.html` always shows Asset Curation / Client Progress / Sign-off / Workstreams / Feedback — Sign-off is meaningless on a live-edit engagement (it never gets signed off, it gets submitted), and Submissions — the thing that actually matters for the two live engagements — isn't a tab at all.
- **A capability that's already built can still fail the "intuitive" test if it's undiscoverable.** Section clone/hide/reorder are live and wired but there's no evidence of a visible entry point beyond hover-triggered UI in `live-edit.js` — worth a direct check with the client on whether they've ever found it, before concluding it needs to be *rebuilt* rather than *surfaced*.

## 6. Proposal

### System architecture — collapse two axes into one field

Replace `modes[]` + `liveEditable` with a single first-class `capability` field on every manifest:

```json
"capability": "live-edit"   // or "review" (legacy, closed to new engagements)
```

- Retire `modes[]` for live-edit engagements entirely — it currently governs nothing there.
- Delete the `posts` capability from `KNOWN_MODES` — zero adoption, remove the option rather than leave it selectable with nothing behind it.
- Add a `group` field so repeated instances of one capability for one client (the 7 treatment microsites) roll up under a shared parent in the data model, not just by string-matching `client` in the admin display layer.
- Merge the two upload pipelines (admin bulk vs. client live-edit) into one shared module: same webp conversion, same validation, trust level driven by *actor* (admin = held, client-in-live-edit = auto-live) rather than two independent multer configs.
- **Add an `uploadedBy` / `owner` field to every asset record** (admin vs. client, plus which client login). Osman's standing rule: admin seeds an engagement's images at build time (first instance), but from that point forward the client owns anything they upload themselves — they should be able to see, replace, or remove their own uploads without touching admin-seeded ones. Today neither pipeline tracks provenance at all, so this needs the merged upload module to write an owner field, and the gallery/library picker (currently one undifferentiated pool) to filter or badge by owner.
- Merge the two clone mechanisms (manifest-defined repeatable region vs. generic section clone) — same underlying operation, two ID-suffix systems and two route namespaces today.
- Give the publish-request flow a real admin panel. It's the tool's most operationally important action and currently the least discoverable.

### Web designer's lens — what to build next, in order

1. ~~Image reorder within multi-image modules.~~ Reframed after investigation — see the 16 Aug zoom/pan-within-frame entry above; the corner-drag resize handle turned out to be a live layout-breaking bug for grid images, addressed with a responsive-safe zoom control instead.
2. ~~Admin copy-editing on live-edit engagements~~ — DONE, see above (turned out to be built-but-broken, fixed by routing through `client-edits.json`).
3. ~~Template/clone-engagement flow~~ — **DONE 16 Aug 2026.** New `POST /api/admin/engagements/:engagement/clone` (`server.js`): copies `prototype/` and `assets/` from a source engagement (excluding `.bak*` files, `output/`, `assets-removed/`) into a new engagement id, writes a fresh `manifest.json` with new `engagement`/`client`, `hiddenFromClient: true` by default, and a `clonedFrom`/`clonedAt` provenance trail. Deliberately does **not** copy `output/` — the clone opens on the source's original unedited content, not its edited state, since `client-edits.json` etc. start fresh. "Clone as template" button added to each live-edit engagement row on `/admin`. **Verified with a real dry run** against `puremed-site` (the internal dev engagement — chosen because it's safe to touch, not a live client site): confirmed correct file exclusions, valid manifest, and that `loadManifest()`/`listEngagements()` pick the clone up correctly; test clone deleted after verification. This directly addresses the sharpest scaling problem flagged in §4 (7 hand-built treatment-microsite folders with no shared lineage).
4. ~~Submission history + rollback~~ — DONE, see above.
5. ~~Cross-page section move~~ — **DONE 16 Aug 2026.** New `POST /api/client-edits/:engagement/section/:id/move` + `.../move/cancel` (`live-edit-routes.js`), plus `edits.sections.moved: [{id, fromPageId, toPageId, html, movedAt}]` added to the edits schema. Kept inside the same overlay-only trust model as everything else — never touches the underlying static HTML files. The section's `outerHTML` travels with the move (sanitized the same as copy edits) since the target page's static file doesn't contain that section at all; the source page hides it via the existing hide mechanism; the target page injects it at boot from `edits.sections.moved` (`applyMovedSections()` in `live-edit.js`), with a "Moved from X" badge and a way to move it back. **Known limitation, called out in the digest:** the Astro publish pipeline ("Loop 2") doesn't parse `sections.moved` yet — a move shows correctly in Stage and gets flagged in the publish-request digest for manual merge, but isn't auto-applied to the Astro source. Same category of deferred integration as the clone-mechanism merge in Phase 2 — don't teach Loop 2 to parse this without reading its actual code first.
6. ~~Mobile/responsive preview toggle in the editor.~~ — **DONE 16 Aug 2026.** A "📱" toggle in the editor's toolbar opens a fixed-size iframe (390×844) of the page's own URL — a true narrow viewport, not a CSS transform trick (which wouldn't trigger the site's actual mobile media queries). Shows the last-saved state, same as any other visitor would see.

**Phase 3 is complete as of 16 Aug 2026.** All six items shipped, deployed clean (`pm2 restart` verified with no errors after every change), and the clone-engagement flow was functionally verified with a real dry run, not just a syntax check. Every change stayed inside the existing overlay-only trust model except the cross-page move's known Loop 2 gap, which is explicitly flagged rather than silently assumed to work.

### UX — one door, not three

- Client sees **one capability going forward: "Edit your site."** No card for review, no card for content review.
- Admin's per-engagement tabs are conditional on `capability`: live-edit engagements get Asset Curation / Copy / Submissions / Feedback; legacy review engagements (during wind-down only) keep Asset Curation / Progress / Sign-off. Nothing shows a dead tab for a capability the engagement doesn't have.
- Mark the legacy review engine **"closed to new engagements"** in the admin UI itself, not just in this document — a status label on the engagement list, not tribal knowledge.
- Delete the "content review" concept outright. If social-content review returns as a need, it should reuse live-edit's comment/annotation layer, not resurrect a third data model.

1. **Housekeeping — DONE 16 Aug 2026:** removed the dead `posts` capability from `KNOWN_MODES` (`workstreams-routes.js`); added `archived: true` to `puremed-content` and `fsc-content` manifests (flag, not moved — no path/route risk) and split them into a collapsed "Archived" section on `/admin`, separate from the active client groups; added a per-engagement Submissions tab (`views/admin-partials/submissions.html` + `GET /api/admin/submissions/:engagement` and `.../:n/digest` routes in `live-edit-routes.js`) — submission history + digest text were already captured on disk, just had no UI; added a "Legacy · closed to new work" chip on any non-`liveEditable` engagement row in `/admin`. All changes additive, backed up on the Pi with `.bak-phase1housekeeping-<timestamp>` before overwrite, syntax-checked locally before deploy, `pm2 restart stage` verified clean (no error log output, all routes still redirect-to-login as expected when unauthenticated). Not yet done: visual/functional pass as an authenticated admin — Osman to confirm the Submissions tab renders real digests and the Archived section collapses correctly.
2. **Consolidate primitives — DONE (upload/delete/dedup half) 16 Aug 2026:** built `lib/asset-store.js`, one shared module for both upload pipelines — same webp conversion, same no-duplicate-image rule (content is hashed via `lib/image-meta.js`'s extended cache; a byte-identical file already in the library is never written twice, the existing file is reused instead), same soft-delete removal (recoverable in `assets-removed/`, tombstoned). Every asset now carries an `owner` (`"admin"` or `"client:<username>"`). Admin still uploads/removes anything via the existing Asset Curation tab (now shows a "Client upload" badge); clients can now remove photos they uploaded themselves from the live-edit library picker — ownership-gated (can never touch an admin-seeded or another client's image) and blocked if the photo is currently placed on the site (must swap it out first, so delete can't leave a broken image live). Backfilled the existing library with a one-off reconciliation (`scripts/one-off-completed/dedupe-assets-2026-08-16.js`, dry-run reviewed before applying): found 17 byte-identical duplicates across `puremed-content`, `puremed-laser-facelift-winslow`, and `puremed-micro` (mostly v1/v2, v4/v5 naming variants), consolidated to whichever copy was actually in use/approved, rewrote every reference in `client-edits.json` / `admin-state.json` / `manifest.json` before soft-deleting the losers. Verified: all manifests still valid JSON, no dangling references, meta cache clean. **Admin copy-editing for live-edit engagements — DONE 16 Aug 2026, and it was actually broken, not missing.** The "Copy" tab someone added directly on the Pi (outside this proposal's tracking) wrote to `output/admin-copy.json`, the legacy review engine's overlay file — but `servePrototype()` never reads that file for a `liveEditable` engagement; it only injects the live-edit boot script over the raw static HTML. So every admin edit through that tab was silently discarded — it never reached the page the client actually sees. Confirmed no one had hit this yet (`admin-copy.json` didn't exist for either live engagement). Fixed: `copy-editor.html` now branches on `manifest.liveEditable` — legacy engagements keep the original admin-copy.json path unchanged; live-edit engagements read/write through the *same* routes the client's own inline editor uses (`/api/client-edits/:engagement/copy/:id` + `/revert`), confirmed by cross-checking that `manifest.copy.sections[].id` and `client-edits.json`'s `copy` map use the identical id space (both derived from the same `data-stage-id` autotag pass). An admin pre-fill is now indistinguishable from a client edit — same file, same shape, live immediately.

**Merge the two clone mechanisms — partially done, full merge deferred.** Investigated both in full: repeatable regions (manifest-declared, capped, clean removal that deletes the clone's copy/image edits) vs. generic sections (any `[data-stage-section]`, uncapped, no manifest declaration needed). They're not actually interchangeable — repeatable regions know their own copyIds/imgIds inventory from the manifest; generic sections don't, because nothing declares one. The real bug this surfaced: generic section clones could be created but never truly removed — "Delete" on a clone only ever hid it (`stage-hidden` CSS), permanently, leaving orphaned `edits.copy`/`edits.images` entries with no way to clean them up. Fixed with a new `POST /api/client-edits/:engagement/section/:id/remove` route: the client (which has the clone's DOM in hand) reports which copy/image ids belonged to it, the server deletes the clone entry plus those edit entries. `live-edit.js`'s section toolbar now branches — deleting an original section still hides it (restorable); deleting a clone now truly removes it. **Deferred:** collapsing the two into one ID-suffix system / one manifest schema, which the original proposal called for — this would also touch the Astro publish/apply pipeline ("Loop 2") that consumes `edits.repeatables` and `edits.sections`, and that pipeline's code wasn't audited in this session. Don't attempt the structural collapse without reading it first.
3. **Close the designer-facing gaps:** ~~image reorder~~ **image zoom/pan-within-frame — DONE 16 Aug 2026, see below**; cross-page section move, template/clone-engagement, submission history/rollback, mobile preview.

**Image zoom, pan-within-frame — DONE 16 Aug 2026.** Osman asked for "reposition images within the container they're in." Investigation found drag-to-pan (`objectPosition`) already existed and worked correctly, but the existing corner-drag **resize handle is a live, undiagnosed bug**: it sets the `<img>`'s own `width`/`height` in pixels via inline style, which overrides the page's own responsive CSS (`width:100%` + `aspect-ratio:3/2` is the standard pattern used sitewide, confirmed in both grid contexts like before/after strips and single contexts like hero images — always inside a wrapper with `overflow:hidden`). Using that resize handle on any image in a multi-column grid would silently break the responsive layout on every future page load (the saved width/height gets reapplied by `applyOverlay()` at every boot). No one had hit it yet (checked — no live engagement had a saved width/height edit that would be affected). Left the resize handle itself untouched (still used for at least one legitimate case — a logo pinned to an exact pixel size) but added a parallel, responsive-safe **zoom** control instead: a slider (100–300%) that scales the photo via CSS `transform: scale()` with `transform-origin` tracked to the current pan position — this only ever paints larger inside the existing frame (which the site's own `overflow:hidden` wrapper convention already clips to), never touches the frame's own box dimensions, so it can't break a grid. Pan-drag math (`live-edit.js`'s `startImgDrag`) was reworked to use `offsetWidth`/`offsetHeight` (unscaled layout box) instead of `getBoundingClientRect()` (which would have included the zoom transform and corrupted the object-fit:cover math), and pan headroom now scales with zoom so you can pan further once zoomed in. Fully backward compatible — at zoom=100 (the default for every existing image) all the math reduces to exactly the pre-existing behaviour. New `zoom` field flows through `lib/asset-store`-adjacent `image/:id` route validation (100–400 range), `client-edits.json`, `applyOverlay()` on every page load, and the publish-request digest. Deployed and smoke-tested; **not yet done: Osman's own hands-on pass** dragging the zoom slider on a real image in the browser.
4. **Retire the legacy engine:** once `puremed` (the last parked review engagement) is formally closed, delete `shell.html`, `signoff.js`, and the `review-state.json` model. One engine, one manifest field, one client-facing door.

**Submission history + rollback — DONE 16 Aug 2026.** No new data model needed — every submission already snapshots `copy`/`images`/`repeatables`/`sections` in full (`output/submissions/NNN.json`), it just had no restore action. Added `POST /api/admin/submissions/:engagement/:n/restore`: backs up the current live-edit state to `output/pre-restore-backup-<timestamp>.json` (not a formal submission, just a rescue copy, so a restore is itself always undoable), then overwrites `client-edits.json` with the chosen snapshot. No client-side plumbing needed — `applyOverlay()` already re-renders from `client-edits.json` on every page load, so a restore takes effect the moment anyone reloads the page. "Restore this version" button added inside each submission's expanded digest in the Submissions tab, with a confirm dialog. Deployed clean, routes verified.
