01 Purpose

This document captures the architectural decisions, tooling stack, and operating model for Main Stage Studio's web delivery practice. It serves as the reference point for how client sites are built, hosted, and maintained.

It is a living document. Decisions marked as deferred will be revisited and updated as the practice matures. A separate Tech Strategy document will cover commercial, pricing, and scaling decisions once the stack is proven.

02 Scope

This document covers:

  • The delivery stack used to design and build client websites
  • The hosting infrastructure and its operating model
  • Licensing decisions and their commercial implications
  • The local development workflow

It does not cover:

  • Commercial pricing and client engagement terms — covered in a future Tech Strategy document
  • Brand, positioning, or marketing for Main Stage Studio
  • Project-specific design or content decisions
  • The step-by-step operational runbook — covered in a separate Operational Guide

03 Delivery Stack

3.1 CMS and Page Builder

PlatformWordPress (self-hosted, wordpress.org)
Page BuilderBricks Builder
RationaleDeveloper-grade visual builder with clean code output, class-based styling, and a Webflow-like workflow on WordPress infrastructure. No platform lock-in — if Bricks ceased trading, WordPress sites continue to function. Committed tooling for all Main Stage Studio client delivery.
vs FramerFramer offers faster prototyping for simple brochure sites but introduces platform dependency and limits infrastructure control. Bricks on WordPress aligns with Main Stage Studio's technical depth, agency growth ambitions, and AWS foundational knowledge.
vs ElementorBricks produces cleaner code, is faster, and is better suited to a professional agency delivery model. Elementor's larger ecosystem is not a sufficient trade-off.

3.2 Prototyping

ToolHTML prototypes (Claude-assisted)
UseClient design approval and visual specification prior to Bricks build
RationaleProven in client engagement. Lightweight, browser-renderable, no tooling overhead. Serves as functional spec for Bricks JSON template generation.
FigmaNot in current stack. Identified as a future capability milestone — to be introduced when client scale or engagement complexity justifies the overhead. Saves £144/year at current stage.

3.3 Local Development

ToolLocalWP
PurposeFull WordPress environment running locally. All site builds begin here before going live.
CostFree
Key benefitNo hosting cost during build phase. Local and staging environments do not count against Bricks licence limits.

3.4 AI-Assisted Delivery

PrimaryClaude Pro — strategy, copy, code assistance, architecture, HTML prototyping, thought partnership
SupportingPerplexity — research and market intelligence
PrincipleAI-assisted without it showing. Used throughout delivery but never at the expense of quality or strategic rigour.

3.5 Claude Code Integration

Current statusNot in use
PotentialBricks stores page data as JSON in the WordPress database. Claude Code could connect via SSH to read and write Bricks JSON directly, enabling automated template generation and bulk updates across sites.
Why deferredBricks JSON schema is undocumented and version-sensitive. Database writes carry risk if schema changes. Better to learn the stack manually first and automate once patterns are understood.
Future triggerRevisit when managing 3+ active client sites and repetitive build tasks emerge.

04 Hosting Infrastructure

4.1 Provider

ProviderCloudways
InfrastructureDigitalOcean — London region (UK data residency, GDPR alignment)
ModelManaged cloud hosting. Cloudways manages the infrastructure layer; Main Stage Studio manages the WordPress layer.
RationaleScales linearly without platform migration. Avoids architectural debt of cheap shared hosting. Multiple WordPress installs on one server — no artificial site limits. Compatible with AWS foundational knowledge. No long-term contract.
Multi-siteYes. A single server supports multiple WordPress installs, each with its own domain, database, and file system. A small DigitalOcean droplet (1GB RAM) comfortably handles 3–5 low-traffic brochure sites. Scaling is achieved by resizing the server, not migrating platforms.
Entry costApprox. £10–12/month for a single small server
BillingMonthly, no long-term contract

4.2 Key Concepts

HostingRented space on a server connected to the internet 24/7. Where website files live. Without hosting, a website only exists on a local machine.
ServerA computer owned by the hosting provider, running permanently, serving website files on request.
DomainThe human-readable address (e.g. puremed.uk). Separate from hosting. Must be pointed at the server via DNS.
DNSThe system that connects a domain to a hosting server. Configured once, rarely changed.
WordPress installA copy of WordPress software on the hosting server. One server can hold multiple installs — multiple separate websites.
LocalWPSoftware that simulates a server on a local laptop. Used for development before go-live. Not publicly accessible.
StagingA private copy of a live site on real hosting used for testing changes before publishing.
SSL certificateEnables https:// — required for trust, SEO, and browser compatibility. Provided free by Cloudways.

4.3 Client Hosting Model

Option A — Hosted by Main Stage Studio
  • Client sites on MSS Cloudways account
  • Full environment control
  • Simpler setup per engagement
  • Bundleable into retainer pricing
  • MSS carries hosting cost and responsibility
Current Default
Option B — Client's Own Hosting
  • Client procures and owns their hosting
  • Clean separation — no dependency on MSS
  • Client owns infrastructure fully
  • More setup friction per engagement
  • Better for established clients with technical resource
Decision per engagement. Option A is the default for early-stage clients and low-overhead projects. Option B to be offered as client sophistication increases.

06 Build-to-Launch Workflow

Standard workflow for each client site from brief to live:

1
HTML Prototype
Claude-assisted HTML prototype built for client design approval. Serves as visual spec and functional reference for Bricks build.
2
Local Build
WordPress + Bricks site built in LocalWP. No hosting cost, no licence consumed during this phase.
3
Client Review
Share via LocalWP tunnel or video walkthrough. Iterate until approved.
4
Provision Hosting
Cloudways server provisioned if not already live. New WordPress application added to server.
5
DNS Configuration
Domain DNS updated to point to Cloudways server. SSL certificate provisioned.
6
Deploy
Site migrated from LocalWP to live Cloudways environment.
7
Licence Activation
Bricks Business licence activated on live domain. Counts against licence limit from this point.
8
Go Live
Final checks — SSL confirmed, forms tested, mobile reviewed, performance baseline recorded.
