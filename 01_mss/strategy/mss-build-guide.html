Local Development

LocalWP Installation & First Site

1

Download LocalWP. Go to localwp.com, download the macOS installer. It's a standard .dmg — drag to Applications, launch.

2

Create your first local site. Click + Create a new site. Enter site name: PureMed Aesthetics. LocalWP will suggest a local domain like puremed.local — accept it.

3

Choose environment. Select Preferred (not Custom). This gives you PHP 8.x, MySQL 8.x, Nginx — appropriate for a Cloudways/DO deployment.

Why Preferred: Matches Cloudways server stack closely enough that you won't encounter environment mismatches on migration. Custom is only needed if a plugin requires a specific PHP version.

4

Set WordPress credentials. Create your admin username and password. Record these — you'll use them daily. LocalWP creates the WP install automatically.

5

Click WP Admin. Once the site is running (green indicator), click WP Admin in LocalWP. Your browser opens puremed.local/wp-admin. You're in.

6

Tidy the default install. In WP Admin: delete the Hello Dolly plugin (Plugins → Installed Plugins), delete the sample page and Hello World post, and remove all default themes except Twenty Twenty-Four (you'll delete that too once Bricks is active).

7

Note your local site files path. In LocalWP, right-click your site → Reveal in Finder. Your WP files live inside app/public/. This is where you'll work with themes and uploads locally.

Client Approval Tool

GitHub Pages — HTML Prototype Delivery

The workflow: Claude builds an HTML prototype → you push to GitHub → client gets a live URL to review before any WordPress build begins. No hosting cost, no CMS overhead.

1

Create a repo for the project. On GitHub, create a new repo: puremed-prototype. Set it to Public (required for free GitHub Pages). Initialise with a README.

Why Public: GitHub Pages is free only on public repos (on the free plan). Since these are prototypes — not production code — public is fine. If you want private repos with Pages, upgrade to GitHub Pro (£4/mo).

2

Clone the repo locally.

git clone https://github.com/YOUR_USERNAME/puremed-prototype.git
cd puremed-prototype
3

Add your prototype HTML. Drop Claude's output into the repo root as index.html. Any linked assets (images, fonts if self-hosted) go in subfolders. Inline CSS/JS is simplest — one file, no broken paths.

4

Push to GitHub.

git add .
git commit -m "Initial prototype — PureMed homepage"
git push origin main
5

Enable GitHub Pages. On GitHub: repo → Settings → Pages (left sidebar) → Source: Deploy from a branch → Branch: main, folder: / (root) → Save.

6

Get the live URL. After ~60 seconds, the Pages section shows your URL: https://YOUR_USERNAME.github.io/puremed-prototype/. Share this directly with your client.

Every git push to main auto-deploys. Iterate freely — changes are live within about 60 seconds.

Managed Hosting

Cloudways Account & Server Provisioning

1

Sign up at cloudways.com. Use your business email. Cloudways offers a 3-day free trial — activate it. No credit card required upfront.

2

Choose your cloud provider.

Pick DigitalOcean. You've already decided this — it's the right call. DO is the best price-to-performance at small scale, has solid London presence, and Cloudways' tooling is most mature on DO. AWS on Cloudways costs ~40% more for equivalent specs and adds unnecessary complexity at this stage.

3

Provision your first server. Click Launch → choose provider, region, size.

SettingChoiceWhy
ProviderDigitalOceanBest value + Cloudways integration
RegionLondon (LON1)UK client base, GDPR-aligned data residency
Server Size2GB RAM / 1 vCPU~£17/mo. Handles 2–3 low-traffic brochure sites comfortably. Upgrade is one-click if needed.
PHP StackWordPressPre-optimised stack for WP (Nginx, Redis, Varnish)

Server vs Application: One server hosts multiple WordPress applications. You'll add a new Application (Section 4) per client site — not a new server. The 2GB DO droplet is your container for all MSS brochure sites until you hit resource limits.

4

Wait for provisioning. Takes 5–8 minutes. Cloudways spins up the droplet on DO, installs the stack, and hands you a server IP. You'll see it in your dashboard.

5

Add your SSH key. Go to Servers → Master Credentials → note the SSH username and password. Optionally add your public key under Security → SSH Access for password-free terminal access. Not required for the GUI workflow below, but useful.

Application Setup

Adding a WordPress Application on Cloudways

1

Add an application. From your server dashboard, click Applications → Add Application.

2

Fill in application details.

FieldValue
Application TypeWordPress
Application Namepuremed-aesthetics
Admin EmailYour email or client's
Admin UsernameSomething non-obvious (not "admin")
Admin PasswordStrong, unique — save in password manager
Project NamePureMed Aesthetics
3

Note the temporary URL. Cloudways assigns a staging URL like abc123.cloudwaysapps.com. Use this for all work until DNS is pointed (Section 5). Access WP Admin at abc123.cloudwaysapps.com/wp-admin.

4

Configure key server settings. Under your application → Application Settings: enable Varnish (full-page cache, off during development, on at go-live), Redis Object Cache (on), set PHP version to 8.2.

Leave Varnish OFF during build. Varnish caches pages aggressively — you'll see stale content when editing. Turn it on only at go-live (Section 9).

Domain Routing

DNS Configuration — puremed.uk → Cloudways

1

Get your Cloudways server IP. In Cloudways: Servers → select your server → the IP is shown at the top of the dashboard. Copy it.

2

Add domain to Cloudways application. Application → Domain Management → Add Domain → enter puremed.uk and www.puremed.uk. Do this before changing DNS so Cloudways is ready to serve requests when they arrive.

3

Log in to your domain registrar (wherever puremed.uk is registered — likely 123-reg, GoDaddy, or Namecheap for .uk domains). Navigate to DNS management.

4

Update DNS records.

TypeName / HostValueTTL
A@Your Cloudways server IP300
AwwwYour Cloudways server IP300
CNAMEwwwDelete this if it exists — conflicts with the A record above—

Set TTL to 300 seconds (5 min) before the change so propagation is fast. Restore to 3600 after go-live to reduce DNS query load.

5

Verify propagation. Use dnschecker.org — search puremed.uk, type A. You want green ticks across most nodes. Can take anywhere from 5 minutes to 48 hours; typically <30 min with a low TTL.

6

Update WordPress URL. Once DNS is resolving, go to WP Admin (via the temporary Cloudways URL) → Settings → General. Set both WordPress Address and Site Address to https://puremed.uk. Save. (You'll need HTTPS live first — do SSL in the next section before this step.)

Don't update WP URLs to the final domain until SSL is active or you'll lock yourself out of WP Admin with mixed-content errors. Do Section 6 first, then come back here.

6

HTTPS

SSL Certificate Setup

1

Confirm DNS is fully propagated before proceeding. The Let's Encrypt ACME challenge that Cloudways uses requires DNS to resolve correctly or certificate issuance fails.

2

Issue SSL via Cloudways. Application → SSL Certificate → Let's Encrypt. Enter:

  • Email address (for renewal notifications)
  • Domain: puremed.uk
  • Tick Wildcard if you want subdomains covered (not needed for a simple brochure site — leave unticked)
  • Check www Redirect — this redirects www → non-www automatically

Click Install Certificate. Takes ~30 seconds.

3

Enable HTTPS redirect. On the same screen, toggle Force HTTPS to ON. This adds a 301 redirect from http → https at the server level — more reliable than a WP plugin redirect.

4

Now update WordPress URLs. Back to WP Admin → Settings → General → update both URL fields to https://puremed.uk. Save changes. Your site is now fully on HTTPS.

5

Verify in browser. Visit https://puremed.uk. Padlock should be showing. If you see a mixed-content warning (padlock with warning), use the plugin Really Simple SSL to scan and fix any hardcoded HTTP URLs in content.

Cloudways auto-renews Let's Encrypt certificates every 90 days. You don't need to do anything.

Page Builder

Bricks Builder — Licence, Installation & Activation

1

Purchase Business licence. Go to bricksbuilder.io/pricing. Business = unlimited sites, which is correct for an agency context. Cost is ~€149/yr. Pay, download the bricks.zip file, and note your licence key from the confirmation email.

Why Business (not Personal): Personal limits you to one site. You'll be adding new client sites regularly — Business pays back on site two. It also includes white-label mode if you ever want to hide the builder from clients.

2

Install on LocalWP first. In your local WP Admin → Plugins → Add New → Upload Plugin → select bricks.zip → Install Now → Activate.

3

Activate licence locally. WP Admin → Bricks → Licence → paste your key → Activate. You're now building locally with Bricks.

4

Install on Cloudways (live site). Access your Cloudways WP Admin → repeat the plugin upload process. Paste the same licence key → Activate.

Bricks licence activations are domain-tied. LocalWP local domains (e.g. puremed.local) count as development domains and don't consume licence slots.

5

Set Bricks as the active theme. Appearance → Themes → Activate Bricks. You can now delete the default Twenty Twenty-Four theme.

6

Configure Bricks settings. Bricks → Settings. Key settings on first run:

  • Post Types: Enable Pages and any CPTs you'll build with Bricks
  • Gutenberg: Disable Gutenberg editor for post types where Bricks is active — keeps the UI clean
  • Template Library: Leave enabled — useful for importing Bricks community templates as starting points
  • Custom Breakpoints: Set breakpoints to match your design system early (default is fine to start)
7

Enter the builder. Edit any page → click Edit with Bricks. The visual editor loads. Left panel = elements; right panel = style controls; canvas = live preview. The learning curve is moderate but logical — structure first (Section/Container/Div), then elements inside.

Deployment

Migrating LocalWP → Cloudways

Use the Migrate Guru plugin — it's free, handles large sites, performs a direct server-to-server transfer (no download/upload of zip files), and is specifically optimised for Cloudways.

1

Install Migrate Guru on your local site. WP Admin (LocalWP) → Plugins → Add New → search "Migrate Guru" → Install & Activate.

2

Get your Cloudways SFTP credentials. Cloudways → Application → Access Details → note: Public IP, Application Username, Application Password, SFTP Port (typically 22). You'll need these in the next step.

3

Run the migration. In Migrate Guru (local WP Admin) → enter your email → click Migrate → select Other Host (Cloudways is on the dropdown but "Other" with manual SFTP creds is more reliable).

Enter the SFTP details from Step 2. The migration path field should be the application's document root — Cloudways shows this under Access Details as something like /home/APP_USER/htdocs/YOUR_APP_NAME.cloudwaysapps.com/public_html.

4

Monitor progress. Migrate Guru emails you updates. The transfer runs server-to-server; you don't need to keep the browser open. For a small brochure site, expect 10–20 minutes.

5

Update site URL on Cloudways. After migration completes, log in to WP Admin via the Cloudways temporary URL (abc123.cloudwaysapps.com/wp-admin). Go to Settings → General → change both URL fields from your local domain (puremed.local) to your Cloudways temporary URL. Save. Verify the site loads correctly.

Don't skip this step. WP stores the site URL in the database. If it still says puremed.local, all redirects and asset paths will break on the live server.

6

Search-replace remaining local references. After verifying the site works on the temp URL, use Better Search Replace plugin to find/replace any remaining puremed.local strings in the database. Replace with https://puremed.uk. Tick "Run as dry run" first to see what would change, then run for real.

7

Re-activate Bricks licence on the live domain. After DNS is pointed and WP URLs are updated to https://puremed.uk, go to Bricks → Licence → the domain will have changed. Re-activate with your key to bind it to the live domain.

Final Checks

Go-Live Checklist

Run through this top-to-bottom before sharing the live URL with your client.

DNS & HTTPS

  • DNS fully propagated (dnschecker.org)
  • SSL padlock showing, no mixed-content warnings
  • http:// redirects to https://
  • www redirects to non-www (or vice versa — consistent)

WordPress Core

  • WP Site URL and Home URL both set to live domain
  • All plugins up to date
  • Admin username is not "admin"
  • Strong admin password set
  • WP debug mode OFF (WP_DEBUG false)
  • File editor disabled in production
  • WordPress version up to date
  • Unused plugins deleted (not just deactivated)

SEO & Visibility

  • Settings → Reading: "Discourage search engines" is UNCHECKED
  • SEO plugin installed (Rank Math or Yoast)
  • Meta title and description set on homepage
  • XML sitemap generated and submitted to Google Search Console
  • Google Search Console property added and verified
  • Favicon set (WP Customiser → Site Identity)

Performance & Caching

  • Varnish cache ENABLED (Cloudways dashboard)
  • Redis object cache ENABLED
  • Images optimised (Cloudflare Images or Smush)
  • Google PageSpeed score checked (target 80+ mobile)
  • No console errors in browser dev tools
  • CDN enabled if needed (Cloudways has Cloudflare integration)

Content & Forms

  • All links tested — no 404s
  • Contact form tested end-to-end (submission → email received)
  • SMTP email sending configured (not PHP mail — use WP Mail SMTP)
  • All images have alt text
  • Privacy Policy page published
  • Cookie consent banner active (if handling personal data)
  • All placeholder / Lorem Ipsum text removed
  • Mobile layout reviewed on real device

Backups & Security

  • Cloudways automated backups enabled (daily, 7-day retention)
  • Backup frequency confirmed in Cloudways dashboard
  • Cloudflare or Cloudways Bot Protection enabled
  • WP login URL optionally changed (WPS Hide Login plugin)

Final step: Take a manual Cloudways snapshot backup immediately before going live. Label it "Pre-launch snapshot — [date]". If anything breaks after go-live, you have a clean restore point.
