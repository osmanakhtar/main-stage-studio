What is placeholder
Letters of engagement, retainers, due-diligence forms and clinical consent forms are marked Placeholder. All are professionally drafted, authored by a firm's own advisers or by clinicians and reviewed by indemnity providers. Writing convincing versions here would make the prototype look more finished than it is.
What connects next
Calendar, payments and identity verification are integration points, chosen per practice rather than assumed here. Availability in this prototype is computed live from a working pattern and a set of busy blocks, so the scheduling logic is already doing the real work. Connecting a live calendar changes the source, not the engine, and the same holds for taking payment and verifying identity.

Every requirement the client is shown appears here first, with the rule that produced it. Nothing is asked for that cannot be explained by a numbered row. This is the compliance artefact, not a debug view.

Each rule is configuration, not code: the practice sets what applies to which service in its own admin panel, and the journey recalculates immediately. Nothing here is hardcoded to this business, and nothing changes without the practice choosing it.

Regulatory note
Nothing in this prototype has had legal or compliance review. It demonstrates a design approach, it is not a compliance assurance. Lawful basis, retention and the boundary of what any supplier can be accountable for are specified in the architecture plan and require a practice's own review before any live use.
Determinism
No randomness, no inference, no language model in the decision path. Availability is a pure function of the working pattern, imported busy time, buffers and notice period. Requirements are a pure function of the service selected and the practice's settings.
