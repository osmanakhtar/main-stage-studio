Main Stage Studio · Platform design

Main Stage Aesthetics Studio

One platform under the PureMed estate: website and CMS, opt-in email, social engine, booking and the client's view of all of it. It is built on a shared person record and event log, so it behaves the same way for every tenant and can carry over to the next niche.

Before this goes further

Three decisions that change what gets built

D1 · Decided 26 Sep

This reverses locked v5 positioning

On 4 August MSS locked regulated professional services as the vertical, dropped clinics for lack of track record, and deferred a self-serve tier. An aesthetics-first platform sold as the core offer goes against all three. PureMed is now real sector proof, so there's a case for it, but it needs deciding.

Decided: framed as the Systems line made repeatable, with aesthetics as the first edition because the proof is there. Logged in the decisions log.

D2 · Decided 26 Sep

"Aesthetics" in the platform name limits it

A salon or physio shouldn't buy a product with another industry in its name. The name you chose is right for what clinics buy.

Decided: the platform is Main Stage Studio. Editions carry the niche: Main Stage Aesthetics Studio first, then others.

D3 · Decided 26 Sep

Faces comes in house

One ecosystem for customer records and bookings. The platform replaces Faces Consent: records, consent forms and diary move across, and Faces is retired. There's no integration, no booking-email parsing, and no dual running past cutover.

What it changes: the customer record and consent engine are needed at cutover, and the DPIA now blocks Phase 2. Notes, photos and prescribing can follow, because Faces doesn't hold them today.

The spine

One person, one history

  • One Person per human per tenant, shared by every module
  • One consent ledger, checked at send time
  • One append-only event log: the timeline and the audit trail
  • One rules engine and one workflow engine

Modules keep their own engines. They share this.

Email integration · decided 26 Sep

Everything through care@puremed.uk

Each tenant connects one business mailbox as its only email integration point. For PureMed that is care@, which is already the only user and the admin on its Workspace. There's no third-party email service and no invented sending addresses.

The governing principle

Deterministic, across every module

Same configuration version, same inputs: same journey, price, documents, messages, schedule and published content, every time, with a record of why.

1Rules are data

Every requirement, segment, price and send condition is a row with an ID, evaluated by a pure function.

2Every change is an event

One append-only log with actor, cause and config version. Replay rebuilds state.

3Snapshot, don't reference

Records keep the price, template version and rule IDs in force when committed.

4Time is explicit

Due times come from stored inputs and tenant timezone, never from when a cron wakes.

5Side effects are idempotent

Every send, publish and charge has a key. Overlapping workers can't double-send.

6No LLM in a decision

AI drafts, a person approves, lint checks. AI never decides who gets what or when.

The existing gates (make trace, make datamap, make figures, make preflight) become platform release gates. The booking service failed the determinism and data-protection reviews on 18 August. Those findings (no event log, no booking snapshot, an identifier used as a credential, no DPIA) are fixed in the spine, not patched per module.

Client console

What the clinic sees

The console lets the client see and control a service MSS runs. It opens on what needs them, not on a dashboard.

When did this client last book?People list column and Person header, derived from events.
What was the last action, and why?Activity feed and timeline, each row with its workflow and rule.
How do I create a campaign?Campaigns → New: goal, audience, channels, content, schedule.
How do I start a workflow?Workflows → Library → set parameters → simulate → turn on.
What is the automation doing now?Run view: who is on which step, next action and when.
Is any of it working?Today figures. Tap any number to see the records behind it.

Transferability

Core, pack, tenant

Counts are register rows by scope. Most of the platform isn't specific to aesthetics.

160

Core

Spine, generic modules, console, gates. Every tenant in every niche.

23

Aesthetics pack

Catalogue fields, recall rules, prescriber rules, advertising lint, workflow templates, DPIA, the clinical module. Data plus optional modules, never a core edit.

3

PureMed tenant

Faces migration and exit, forward diary cutover, care@ as the mailbox, Whitehouse CQC routing. Plus brand, catalogue and staff as config.

Earn the word before using it. Call it "transferable" only once one tenant in another niche (salon, physio, accountant) is running with zero core code change (COM-005). Vera proved the content side on 24 July. The operational side hasn't been tested yet.

Phasing

Each phase ships something PureMed uses

0

Spine and the first workflow

Person, consent, events, tags, workflow engine, capture endpoint, email sending. The tired-eyes opt-in runs on it instead of PHP.

Proves the spine carries a real workload.

1

Console v1

Inbox, People, Person timeline, Activity, workflow run view, pause-all switch.

Proves the client can see and control automation.

2

Faces in house

Customer record and consent engine, with the Faces form library unchanged. Faces export verified, migrated and reconciled. Forward diary moved, the platform becomes the only calendar writer, and Faces is retired. Deposits on every booking. Recall and no-show workflows.

Proves one ecosystem for customer records and bookings.

3

Campaigns and reporting

Campaign object, audience preview, stated attribution, Today figures, monthly report from the same queries.

Proves "drive bookings" is measurable.

4

Social publishing and blog

Meta publishing, UTM, post metrics, blog as content, editing surface off the Pi.

Proves the content loop closes.

5

Rest of the clinical pack

Treatment notes and batch tracking, prescribing record, clinical photography, treatment plans (S8 to S11).

Proves the aesthetics edition is complete.

6

Second niche

A non-aesthetics pack and tenant with zero core change.

Proves transferability.

The DPIA now blocks Phase 2. Bringing Faces in house puts health data and signed consent into the platform at cutover. The DPIA and a verified Faces export both have to be done before Phase 2 starts.

Phase 0 trade-off: putting the opt-in on the spine is slower than the PHP route, but it leaves no lead store to migrate later. If the guide has to go live within days, ship PHP as a disposable stop-gap with an export and label it that way in its README.
